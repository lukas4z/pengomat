# Pengomat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A cozy German Secret-Santa site ("Pengomat") with a participant link and a host link, a secret draw, and a shake-the-gift reveal.

**Architecture:** One Next.js app on Vercel. All rules about who may see what live in a pure `service` layer over a tiny `Store` interface (compare-and-set on one JSON document); route handlers are thin wrappers. The UI is hand-built SVG scenery in a sticker style plus supplied Peng images.

**Tech Stack:** Next.js 15 (App Router, TypeScript, `src/`), React 19, plain CSS (globals + CSS Modules), `motion` for the gift animation, `@upstash/redis`, Vitest, Playwright (pre-installed, only for the final browser run).

**Spec:** `docs/superpowers/specs/2026-11-18-pengomat-design.md`

## Global Constraints

- All UI copy in German, Du-form, warm and short.
- Event date: `2026-12-26T00:00:00+01:00`.
- Name 2–30 characters after trimming; 1–3 wishes, each 1–200 characters after trimming; budget free text ≤ 40 characters; max 50 participants; draw needs ≥ 3.
- Host responses never contain wish text, tokens, token hashes or assignments.
- Tokens: 32 random bytes, base64url; only the SHA-256 hex hash is stored.
- Host key from env `HOST_KEY`, compared in constant time; wrong key → 404.
- Redis env: `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN`, falling back to `KV_REST_API_URL`/`KV_REST_API_TOKEN`. Neither set → in-memory store (local dev and tests).
- Audio and music: CC0/public domain files stored in `public/audio`, or Web Audio synthesis. Sources listed in `CREDITS.md`.
- Sticker look: flat fills, dark rounded outlines, no gradients-as-decoration, no emoji as decoration.
- Respect `prefers-reduced-motion`.
- Mobile-first (390 px wide), must hold at 1280 px.

## Review Focus

1. Personal link opened where `localStorage` is unavailable (in-app browser, private mode) → the `?t=` token in the URL alone must log the person in. (Task 4)
2. Two people submit the same name at the same moment → exactly one succeeds. (Task 2)
3. Names with emoji, surrounding whitespace, or HTML → trimmed, rendered as plain text, long names truncated on the sock. (Tasks 2, 5)
4. A participant removed by the host still holds a token → their page falls back to the form with a friendly note, no error screen. (Task 4)
5. Motion permission denied or no motion sensor → tapping/dragging the gift still counts shakes. (Task 6)

Shared types (`src/lib/types.ts`), used by every task:

```ts
export type Phase = 'signup' | 'drawn';
export interface Participant {
  id: string; name: string; wishes: string[]; joinedAt: string;
  tokenHash: string; givesTo?: string;
}
export interface State {
  version: number; phase: Phase; budget: string;
  drawnAt?: string; participants: Participant[];
}
export interface PublicState { phase: Phase; budget: string; eventDate: string }
export interface Me {
  id: string; name: string; wishes: string[];
  phase: Phase; budget: string;
  match?: { name: string; wishes: string[] };
}
export interface HostParticipant { id: string; name: string; joinedAt: string; wishCount: number }
export interface HostView { phase: Phase; budget: string; drawnAt?: string; participants: HostParticipant[] }
export type ErrorCode =
  | 'invalid' | 'name_taken' | 'closed' | 'full' | 'unauthorized'
  | 'not_found' | 'too_few' | 'already_drawn';
export class ServiceError extends Error { constructor(public code: ErrorCode) { super(code); } }
```

### Task 2: Rules — validation, draw, store, service

**Files:** `src/lib/types.ts`, `validate.ts`, `draw.ts`, `store.ts` (interface + `MemoryStore`), `service.ts`; tests `tests/validate.test.ts`, `tests/draw.test.ts`, `tests/service.test.ts`.

**Interfaces — Produces:**

```ts
// validate.ts — throw ServiceError('invalid') on violation
parseName(v: unknown): string
parseWishes(v: unknown): string[]      // trims, drops empty, needs 1–3
parseBudget(v: unknown): string        // may be ''
// draw.ts
drawChain(ids: string[], randInt?: (n: number) => number): Record<string, string>
// store.ts
interface Store { read(): Promise<State>; write(next: State, expectedVersion: number): Promise<boolean> }
class MemoryStore implements Store
// service.ts — every function takes the store first
publicState(s): Promise<PublicState>
join(s, input: {name: unknown; wishes: unknown}): Promise<{token: string; me: Me}>
getMe(s, token: string): Promise<Me>                    // unauthorized if unknown
updateWishes(s, token, wishes: unknown): Promise<Me>    // closed after draw
hostView(s): Promise<HostView>
setBudget(s, budget: unknown): Promise<HostView>        // closed after draw
removeParticipant(s, id): Promise<HostView>             // closed after draw; not_found
reissueToken(s, id): Promise<{token: string}>           // any phase; old token dies
draw(s): Promise<HostView>                              // too_few (<3); already_drawn
reset(s): Promise<HostView>                             // clears participants/draw, keeps budget
```

`service` mutations go through one internal `mutate(store, fn)` that reads, applies `fn`, writes with `expectedVersion`, and retries up to 5 times on a lost race. `drawChain` shuffles (Fisher–Yates with `crypto.randomInt` by default) and maps each id to the next, last to first.

### Task 3: Redis store and API routes

**Files:** `src/lib/store.ts` (add `RedisStore`, `getStore()`), `src/lib/http.ts`, all `src/app/api/**/route.ts`; test `tests/routes.test.ts`.

**Interfaces:**
- Consumes: everything from Task 2.
- Produces: the routes below. Participant token in header `x-peng-token`; host key in header `x-host-key`. Errors are `{ error: ErrorCode }` with status: invalid 400, unauthorized 401, not_found 404, name_taken/closed/full/too_few/already_drawn 409.

| Route | Method | Body | Returns |
|---|---|---|---|
| `/api/state` | GET | – | `PublicState` |
| `/api/join` | POST | `{name, wishes}` | `{token, me}` |
| `/api/me` | GET / PATCH | – / `{wishes}` | `Me` |
| `/api/host/participants` | GET | – | `HostView` |
| `/api/host/participants/[id]` | DELETE | – | `HostView` |
| `/api/host/participants/[id]/link` | POST | – | `{token}` |
| `/api/host/budget` | PUT | `{budget}` | `HostView` |
| `/api/host/draw` | POST | – | `HostView` |
| `/api/host/reset` | POST | `{confirm: 'PENG'}` | `HostView` |

`RedisStore` keeps the whole `State` as JSON in key `pengomat:state`; `write` is one Lua `EVAL` that sets the value only if the stored `version` equals `expectedVersion`. `getStore()` returns a module-level singleton (`RedisStore` if env present, else `MemoryStore`). `http.ts`: `requireHost(req)` (throws `not_found` on missing/wrong key or unset `HOST_KEY`), `tokenOf(req)`, `handle(fn)` mapping `ServiceError` to a response. All routes `export const dynamic = 'force-dynamic'`.

### Task 6: Reveal

**Files:** `src/components/Reveal.tsx`, small additions to `scene/Gift.tsx`.

**Interfaces:** Consumes `Me` (with `match`), `<Gift>`, `<Peng pose="reveal">`, `useSound()` from Task 7 (call through a no-op until then). Produces `<Reveal me={me} />`.

Behavior:
- Full-screen scene, gift centered, prompt "Schüttel mich!", three bells as progress.
- A shake is counted from either source, with a 600 ms cooldown between counts:
  - device motion: acceleration magnitude change above a threshold (start at 18 m/s², tune on a phone if possible);
  - pointer: a tap on the gift, or a drag that reverses direction twice.
- First tap on the gift calls `DeviceMotionEvent.requestPermission()` where it exists; a rejection or absence is silently ignored and that same tap counts as a shake.
- Each shake: wobble animation growing with the count (`motion`), rattle sound, `navigator.vibrate?.(60)`.
- Third shake: lid pops off, sparkle burst, card rises: "Du beschenkst **{name}**", wish list, budget.
- localStorage flag `pengomat-revealed` → on later visits show the card directly with "Nochmal auspacken".
- Reduced motion: no wobble/burst, simple fade; three taps still required.

- [ ] **Step 1:** Implement.
- [ ] **Step 2:** Verify with Playwright (mobile viewport, no motion sensor): three taps reveal the match name and wishes; two taps do not; reload shows the card directly; dispatching synthetic `devicemotion` events also counts.
- [ ] **Step 3:** Commit.
